# JSON vs YAML: 데이터 직렬화 언어 비교

데이터를 구조화하여 저장하고 전송하기 위해 가장 널리 쓰이는 두 형식인 **JSON(JavaScript Object Notation)**과 **YAML(YAML Ain't Markup Language)**을 비교합니다. 두 형식은 서로 호환성이 높지만, 설계 철학과 사용 목적에서 뚜렷한 차이를 보입니다.

## 1. 개요 및 설계 철학

| 구분 | JSON | YAML |
| --- | --- | --- |
| **탄생 배경** | 자바스크립트 객체 문법에서 파생 | 사람이 읽기 쉬운 데이터 중심 언어 표방 |
| **주요 목적** | 데이터 전송 및 API 통신 | 설정 파일(Configuration) 및 가독성 강조 |
| **확장자** | `.json` | `.yaml` 또는 `.yml` |
| **특징** | 기계적인 파싱이 빠르고 명확함 | 주석 지원 및 직관적인 계층 구조 |

---

## 2. 주요 차이점 분석

### 가독성 및 문법 (Readability & Syntax)

* **JSON:** 중괄호`{}`와 대괄호`[]`를 사용하여 데이터의 시작과 끝을 명확히 구분합니다. 문법이 엄격하여 쉼표 하나만 틀려도 오류가 발생합니다.
* **YAML:** 들여쓰기(Indentation)를 사용하여 계층을 구분합니다. 불필요한 기호가 적어 가독성이 뛰어나며, JSON의 상위 집합(Superset)이므로 모든 JSON 데이터는 YAML로 해석될 수 있습니다.

### 주석 지원 (Comments)

* **JSON:** 공식적으로 주석을 지원하지 않습니다. 설정 파일로 사용할 때 큰 단점이 됩니다.
* **YAML:** `#` 기호를 사용하여 자유롭게 주석을 작성할 수 있어, 클라우드 인프라 설정(IaC)이나 애플리케이션 환경 설정에 최적화되어 있습니다.

### 데이터 타입 처리

* **JSON:** 문자열은 반드시 큰따옴표(`"`)를 사용해야 합니다.
* **YAML:** 따옴표 없이도 문자열 표현이 가능하며, 숫자, 불리언, 날짜 등 다양한 데이터 타입을 자동으로 인식합니다.

---

## 3. 코드 비교 예시

동일한 데이터를 두 형식으로 표현했을 때의 차이입니다.

**JSON 형식**

```json
{
  "server": {
    "name": "Production_Server",
    "ports": [80, 443],
    "active": true
  }
}

```

**YAML 형식**

```yaml
server:
  name: Production_Server
  ports:
    - 80
    - 443
  active: true # 서비스 활성화 여부

```

---

## 4. 성능 및 보안 고려사항

1. **파싱 속도:**
* **JSON**은 문법이 단순하여 YAML보다 파싱 속도가 훨씬 빠릅니다. 대량의 데이터를 네트워크로 전송하는 API 응답에는 JSON이 유리합니다.
* **YAML**은 복잡한 문법 구조와 계층 계산 때문에 상대적으로 파싱 속도가 느리고 메모리 소모가 큽니다.


2. **보안:**
* YAML은 **참조(Anchors & Aliases)** 기능을 지원하는데, 이를 악용하여 순환 참조를 일으키는 'Billion Laughs Attack'과 같은 서비스 거부(DoS) 공격에 노출될 수 있습니다. 신뢰할 수 없는 소스의 YAML을 파싱할 때는 주의가 필요합니다.



---

## 5. AWS 및 클라우드 환경에서의 선택 기준

AWS를 포함한 클라우드 서비스 운영 시 환경에 맞는 형식을 선택해야 합니다.

* **CloudFormation 템플릿:** JSON과 YAML을 모두 지원하지만, 가독성과 주석 처리 때문에 **YAML**이 표준처럼 사용됩니다.
* *주의:* CloudFormation 자체는 무료이나, YAML에 정의된 리소스(예: 고사양 RDS 인스턴스)가 생성되면 즉시 **시간당 과금이 발생**하므로 배포 전 비용을 반드시 확인해야 합니다.


* **Lambda 및 API Gateway:** 마이크로서비스 간의 데이터 교환에는 가벼운 **JSON**이 선호됩니다. 페이로드 크기가 작을수록 전송 비용과 레이턴시를 줄일 수 있습니다.
