# 로컬 호스트에서의 Git 서버 접근 전략

Git 서버를 운영하는 호스트(본인 PC)에서 자신의 서버로 접속하여 작업을 할 때도 **별도의 작업 디렉토리(Working Directory)**는 필수적이나, **SSH 접속**은 선택 사항입니다. 이 구조를 이해하기 위해 '저장소의 물리적 분리'와 '접속 프로토콜' 두 가지 측면을 구분해야 합니다.

## 1. 별도 디렉토리 생성: 필수 (Must)

서버 역할을 하는 디렉토리는 앞서 언급한 대로 `--bare` 옵션으로 생성된 **순수 저장소**입니다. 여기에는 소스 코드가 파일 형태로 존재하지 않고 Git 데이터베이스만 존재합니다. 따라서 코드를 수정하고 빌드하려면, 같은 컴퓨터 안이라도 반드시 **별도의 폴더**에 `clone`을 받아야 합니다.

* **서버 폴더 (Bare):** `/srv/git/project.git` (파일 수정 불가, 저장소 역할)
* **작업 폴더 (Work):** `~/dev/my-project` (여기서 코딩 수행)

## 2. 접속 프로토콜 선택: SSH vs Local Path

자신의 컴퓨터에 있는 저장소를 가져올 때는 두 가지 방법이 있으며, 상황에 따라 선택합니다.

### 방법 A: 로컬 파일 경로 사용 (권장 - 가장 빠름)

굳이 SSH라는 네트워크 프로토콜을 거칠 필요 없이, 파일 시스템 경로를 통해 직접 복제합니다. 네트워크 오버헤드가 없어 속도가 가장 빠릅니다.

* **명령어:**
```bash
# SSH 주소 대신 절대 경로를 입력
git clone /srv/git/project.git

```


* **장점:** 설정이 필요 없음, 속도가 매우 빠름.
* **단점:** "네트워크를 통한 접속" 환경을 테스트할 수 없음.

### 방법 B: SSH 루프백 접속 (테스트 목적)

마치 외부인 것처럼 `localhost`를 통해 자신에게 SSH로 접속하는 방식입니다. 주로 SSH 설정(포트 포워딩, 키 인증 등)이 정상적으로 작동하는지 **검증할 때** 사용합니다.

* **명령어:**
```bash
git clone ssh://user@localhost/srv/git/project.git

```


* **필수 설정 (Self-Authentication):**
자신이 자신에게 접속하더라도 인증은 필요합니다. 따라서 본인의 공개키(`id_rsa.pub`)가 본인의 `authorized_keys` 파일에 등록되어 있어야 합니다.
```bash
# 내 공개키를 승인된 키 목록에 추가 (자가 인증)
cat ~/.ssh/id_rsa.pub >> ~/.ssh/authorized_keys

```



## 3. 요약 비교표

| 구분 | 로컬 파일 경로 (`/path/...`) | SSH 루프백 (`ssh://...`) |
| --- | --- | --- |
| **목적** | 실제 개발 및 작업 효율성 극대화 | 네트워크/권한 설정 테스트, 통일된 리모트 주소 사용 |
| **속도** | 최상 (디스크 I/O 속도) | 보통 (암호화/복호화 오버헤드 존재) |
| **인증** | 불필요 (파일 시스템 권한 따름) | 필수 (SSH Key 또는 비밀번호) |
| **복잡도** | 낮음 | 높음 (키 등록 필요) |

### 결론

개발 효율성을 위해서는 **방법 A(파일 경로)**를 사용하는 것이 일반적이며, 서버 설정을 점검하거나 팀원들에게 공유할 URL을 미리 테스트하고 싶을 때만 **방법 B(SSH)**를 사용합니다.
