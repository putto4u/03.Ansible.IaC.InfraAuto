Ansible 플레이북 제작 방법을 실무에서 자주 접할 수 있는 \*\*'간단한 3티어 웹 서비스 배포 환경'\*\*을 예로 들어 좀 더 자세하고 구체적으로 설명해 드리겠습니다. 이 환경은 **웹 서버**와 **DB 서버**로 구성됩니다.

-----

## 실무 기반 Ansible 플레이북 제작 시나리오 🛠️

### 목표 환경

1.  **웹 서버 (Web Tier)**: Ubuntu에 **Nginx**를 설치하고, 배포용 웹 파일 복사.
2.  **DB 서버 (DB Tier)**: Ubuntu에 **MariaDB**를 설치하고, 초기 데이터베이스를 생성.

### 파일 구조 (Role 사용)

실무에서는 복잡성을 줄이고 재사용성을 높이기 위해 \*\*Role(역할)\*\*을 사용합니다.

```
/role_pj/
├── inventory.ini             # 관리 대상 정의
├── site.yml                  # 메인 실행 플레이북
└── roles/
    ├── webserver/            # 웹 서버 역할 정의
    │   └── tasks/
    │       └── main.yml      # Nginx 설치 및 파일 복사 작업
    └── mariadb/              # DB 서버 역할 정의
        └── tasks/
            └── main.yml      # MariaDB 설치 및 DB 생성 작업
```

## 1\. 인벤토리 및 메인 플레이북 작성

### 1.1. 인벤토리 파일 (`inventory.ini`)

```ini
[webservers]
# 웹 서비스 애플리케이션이 구동될 서버 IP
web1 ansible_host=192.168.1.10

[dbservers]
# 데이터베이스 서버 IP
db1 ansible_host=192.168.1.20

[all:vars]
ansible_user=ubuntu
# 보안 강화를 위해 키 파일 경로는 외부에서 전달하거나 SSH Config 사용 권장
# ansible_ssh_private_key_file=/path/to/your/key.pem
```

### 1.2. 메인 실행 플레이북 (`site.yml`)

이 파일은 각 서버 그룹에 대해 미리 정의된 **Role**을 실행하도록 지시합니다.

```yaml
---
- name: 1. Configure Web Servers
  hosts: webservers
  become: yes
  roles:
    - webserver

- name: 2. Configure Database Servers
  hosts: dbservers
  become: yes
  roles:
    - mariadb
```

## 2\. Role별 작업 파일 상세 제작

### 2.1. 웹 서버 Role (`roles/webserver/tasks/main.yml`)

이 태스크는 Nginx를 설치하고, 미리 준비된 웹 파일을 복사한 후 서비스를 재시작합니다.

```yaml
---
# Task 1: Nginx 패키지 설치
- name: Ensure Nginx is installed
  ansible.builtin.apt:
    name: nginx
    state: present
    update_cache: yes

# Task 2: 웹 콘텐츠 파일 복사 (실제 files/ 폴더에 index.html이 있다고 가정)
- name: Copy web application files
  ansible.builtin.copy:
    src: index.html  # roles/webserver/files/index.html 경로에서 가져옴
    dest: /var/www/html/index.html
    owner: www-data
    group: www-data
  notify: restart nginx  # 파일이 변경되었을 때만 Nginx 재시작을 알림

# Task 3: Nginx 서비스가 시작되고, 부팅 시 자동 실행되도록 설정
- name: Ensure Nginx is running and enabled
  ansible.builtin.service:
    name: nginx
    state: started
    enabled: yes

# 핸들러: 파일 변경 시에만 Nginx를 안전하게 재시작합니다.
# handlers/main.yml 파일에 별도로 정의하는 것이 원칙이나, 간단하게 tasks 내에서 명시합니다.
# handlers:
#   - name: restart nginx
#     ansible.builtin.service:
#       name: nginx
#       state: restarted
```

### 2.2. DB 서버 Role (`roles/mariadb/tasks/main.yml`)

이 태스크는 MariaDB를 설치하고, 애플리케이션용 데이터베이스와 사용자를 생성합니다.

```yaml
---
# Task 1: MariaDB 서버 설치
- name: Ensure MariaDB server is installed
  ansible.builtin.apt:
    name: mariadb-server
    state: present
    update_cache: yes
  # 💡 실전 팁: 설치 후 보안 설정을 별도 task로 수행해야 합니다 (mysql_secure_installation 역할)

# Task 2: 애플리케이션용 데이터베이스 생성
- name: Create 'app_db' database
  community.mysql.mysql_db:
    name: app_db
    state: present
    # root 비밀번호는 민감하므로 Ansible Vault 등으로 관리해야 합니다.
    # login_user: root
    # login_password: "{{ vault_db_root_password }}"

# Task 3: 애플리케이션 접속 사용자 생성 및 권한 부여
- name: Create application user and grant permissions
  community.mysql.mysql_user:
    name: app_user
    password: "AppUserStrongPassword" # 실제로는 Vault 사용 필수
    host: "%" # 모든 IP에서 접근 허용 (보안 그룹으로 제한 가정)
    priv: "app_db.*:ALL"
    state: present
  # 💡 실전 팁: 사용자 생성 후 FLUSH PRIVILEGES를 자동으로 수행해줍니다.
```

## 3\. 실행 및 IaC 구현

### 3.1. 실행 명령어

```bash
# -i 옵션으로 인벤토리 파일을 지정합니다.
ansible-playbook -i inventory.ini site.yml
```

### 3.2. 실무적 이점 강조

  * **재사용성 (Role)**: 이 `webserver`와 `mariadb` Role은 다른 프로젝트에서도 파일 경로와 변수만 수정하여 **그대로 재활용**할 수 있습니다.
  * **일관성 (IaC)**: `site.yml` 파일만 실행하면 웹 서버와 DB 서버가 **항상 동일한 설정**으로 동시에 배포됩니다.
  * **멱등성 (Idempotence)**: 이 플레이북을 반복 실행해도, 이미 설치된 Nginx와 생성된 DB/사용자는 변경되지 않으며, 서비스도 불필요하게 재시작되지 않습니다. 이는 곧 **안전한 인프라 관리**를 의미합니다.

## Role 내 다중 YAML 파일 처리 방식

Role 디렉토리 안에 `main.yml` 외에도 `install.yml`, `config.yml`, `setup.yml` 등 여러 개의 YAML 파일이 존재할 수 있습니다. 하지만 Ansible은 **오직 `main.yml`만을 실행의 입구(Entry point)**로 인식합니다.

나머지 파일들은 `main.yml`에서 명시적으로 불러주지 않으면 **절대 자동으로 실행되지 않습니다.** 이를 관리하는 실무적인 방법은 다음과 같습니다.

---

### 1. `import_tasks`를 이용한 파일 통합

가장 일반적인 방법은 `tasks/main.yml` 파일을 일종의 '목차'처럼 사용하는 것입니다.

**`roles/webserver/tasks/main.yml` (메인 파일)**

```yaml
---
- name: 패키지 설치 작업 로드
  ansible.builtin.import_tasks: install.yml

- name: 환경 설정 작업 로드
  ansible.builtin.import_tasks: configure.yml

- name: 서비스 관리 작업 로드
  ansible.builtin.import_tasks: service.yml

```

이렇게 구성하면 Ansible이 `main.yml`을 실행하면서 그 안에 적힌 순서대로 `install.yml` -> `configure.yml` -> `service.yml`을 차례대로 읽어 들여 하나의 작업 리스트처럼 실행합니다.

---

### 2. 조건부 실행 (`include_tasks`)

특정 상황(예: OS가 Ubuntu일 때만 특정 파일 실행)에 따라 다른 파일을 불러오고 싶을 때 사용합니다.

```yaml
---
- name: OS 전용 설정 로드
  ansible.builtin.include_tasks: "{{ ansible_os_family }}.yml"
  # 결과: OS가 Debian 계열이면 Debian.yml을 찾아 실행함

```

---

### 3. 파일 분리 시의 이점 (왜 이렇게 하나요?)

* **가독성:** 한 파일에 수백 줄의 코드가 있는 것보다 기능별(설치, 설정, 보안)로 나누는 것이 훨씬 보기 편합니다.
* **유지보수:** 특정 부분(예: Nginx 설정값)만 수정해야 할 때 해당 파일만 열면 되므로 실수를 줄일 수 있습니다.
* **협업:** 여러 사람이 동시에 하나의 Role을 개발할 때 파일을 나눠 작업하면 충돌을 방지하기 유리합니다.

---

### ⚠️ 주의사항

Role 내부의 `vars/`, `handlers/`, `defaults/` 디렉토리도 마찬가지입니다. `main.yml` 외에 다른 파일을 만들었다면, 반드시 `main.yml` 안에서 `import_scope`나 유사한 방식으로 불러와야 Ansible이 해당 내용을 인지할 수 있습니다.

---

### AWS 환경 내 유료 서비스 알림

* **AWS CloudWatch Logs**: 파일 분할을 통해 상세한 태스크 로그가 발생할 경우, CloudWatch로 로그를 전송하고 있다면 **데이터 수집량(Ingestion) 및 보관(Storage) 비용**이 증가할 수 있습니다.
* **Amazon S3**: 설정 파일들(`configure.yml`에서 사용하는 템플릿 등)을 S3 버킷에서 관리하며 가져올 경우, **GET 요청 횟수와 데이터 전송료**가 발생합니다.
