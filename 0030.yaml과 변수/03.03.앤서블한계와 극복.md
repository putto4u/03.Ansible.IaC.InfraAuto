현대의 클라우드 환경에서 서버 **5대**를 동시에 처리하는 수준으로는 수백, 수천 대의 인스턴스를 관리해야 하는 자동화의 이점을 제대로 누릴 수 없죠.

앤서블이 기본값을 5대로 잡아놓은 것은 성능 한계 때문이 아니라, **"실수했을 때의 피해를 최소화하기 위한 안전장치"**에 가깝습니다. 이 한계를 깨고 사용자님이 생각하시는 효율적인 방식으로 운영하기 위한 핵심 설정과 실무적인 해법을 정리해 드립니다.

---

## 1. 5대의 한계를 넘는 두 가지 방법

### 방법 A: 포크(Forks) 수 늘리기 (병렬 처리 강화)

제어 노드의 사양이 받쳐준다면, `ansible.cfg` 파일이나 명령줄 옵션으로 이 수치를 대폭 늘릴 수 있습니다.

* **설정 변경:** `ansible.cfg`에서 `forks = 50` 또는 `100`으로 수정.
* **효과:** 한 번에 50대, 100대의 서버에 동시 접속하여 작업을 수행합니다. 수백 대 규모라도 순식간에 처리가 가능해집니다.

### 방법 B: 비동기(Async)와 배치(Serial) 조절

 "명령 던지고 나중에 결과 받기" 방식을 극대화하는 전략입니다.

* **`serial` 키워드:** 한꺼번에 100대를 다 건드리는 게 불안하다면, `serial: 20%`와 같이 설정하여 전체의 20%씩 끊어서 진행하되, 각 단계는 비동기로 처리할 수 있습니다.

---

## 2. 왜 기본값이 5대인가? (안전과 비용의 균형)

앤서블 설계자들이 5대를 고집한 이유는 다음과 같은 **AWS 운영 리스크** 때문입니다.

1. **API 속도 제한 (Throttling):**
* 수백 대의 호스트 정보를 동시에 조회하거나 조작하면, AWS API가 이를 공격으로 간주하여 일시적으로 접속을 차단(Throttling)할 수 있습니다.


2. **네트워크 대역폭 폭주:**
* 100대에게 동시에 "1GB 파일 다운로드해"라고 명령을 던지면, 제어 노드의 네트워크 아웃바운드 대역폭이 마비되거나 **데이터 전송 비용(Data Transfer Out)**이 한 번에 과다하게 발생할 수 있습니다.


3. **동시 업데이트의 위험성:**
* 만약 명령에 오타가 있다면? 5대일 때는 바로 중단하면 5대만 망가지지만, 500대라면 서비스 전체가 한순간에 내려가게 됩니다.



---

## 3. 실무적인 결론: 사용자님의 통찰을 적용하는 법

 "결과만 나중에 보내라"는 철학을 현업에서는 다음과 같이 구현합니다.

* **중규모(~100대):** 제어 노드의 사양을 조금 높이고(c5 계열), **Forks 수를 50 정도로 상향**하여 실시간으로 결과를 받으며 빠르게 처리합니다.
* **대규모(500대~):**  **`async`와 `poll: 0`**을 적극 활용합니다. 일단 수백 대에 명령을 쫙 뿌려놓고(Push), 제어 노드는 쉬면서 각 호스트가 작업을 끝내길 기다립니다. 그 후 나중에 결과만 한 번에 수집합니다.

## AWS 과금 및 성능 관련 체크리스트

* **인스턴스 타입:** Forks 수를 50 이상으로 올릴 경우, 제어 노드는 최소 **t3.medium** 이상, 안정성을 위해서는 **c5.large** 이상을 권장합니다. (t2.micro는 5대 이상의 병렬 처리를 견디기 힘듭니다.)
* **EBS 최적화:** 많은 로그를 동시에 기록해야 하므로, 제어 노드의 디스크는 **gp3**를 사용하여 충분한 IOPS를 확보해야 병목 현상이 없습니다. (gp3는 기본 3,000 IOPS까지 무료 범위 내에서 성능을 제공합니다.)

## 1. ansible.cfg 핵심 최적화 파라미터

플레이북 실행 시 매번 옵션을 지정하는 대신, 프로젝트 루트 디렉토리에 `ansible.cfg` 파일을 생성하여 다음과 같이 설정할 수 있습니다.

```ini
[defaults]
# 1. 병렬 처리 개수 (기본값: 5)
# 제어 노드의 CPU 코어당 10~20 정도로 설정하는 것이 일반적입니다.
forks = 50

# 2. 호스트 키 체크 비활성화
# 새로운 EC2 인스턴스 접속 시 yes/no 묻는 과정을 생략하여 자동화를 원활하게 합니다.
host_key_checking = False

# 3. 팩트 수집 캐싱 (성능 향상의 핵심)
# 매번 서버 정보를 긁어오지 않고 파일이나 메모리에 저장해 둡니다.
gathering = smart
fact_caching = jsonfile
fact_caching_connection = /tmp/ansible_fact_cache
fact_caching_timeout = 7200

[ssh_connection]
# 4. SSH 파이프라이닝 (속도 향상의 일등공신)
# 모듈 전송 과정을 줄여 SSH 연결 횟수를 최소화합니다.
pipelining = True

# 5. SSH 커넥션 재사용 (ControlMaster)
# 이미 연결된 SSH 세션을 유지하여 접속 시간을 단축합니다.
ssh_args = -o ControlMaster=auto -o ControlPersist=60s

```

## 2. 주요 설정 상세 설명

### Forks (병렬성 확대)

`forks`는 제어 노드가 동시에 띄울 프로세스의 개수입니다. 5대로 설정되어 있으면 100대의 서버를 관리할 때 20번의 턴을 돌아야 하지만, 이를 50으로 늘리면 2번 만에 끝납니다.

* **주의:** 너무 높게 설정하면 제어 노드의 메모리가 부족해질 수 있습니다.

### Pipelining (통신 최적화)

기본적으로 앤서블은 모듈 파일을 대상 서버의 임시 디렉토리에 복사하고 실행한 뒤 삭제합니다. `pipelining = True`를 설정하면 파일을 복사하는 과정 없이 파이프를 통해 직접 파이썬 인터프리터로 코드를 전달합니다.

* **효과:** 네트워크 왕복 횟수가 줄어들어 전체 실행 시간이 30~50% 단축됩니다.

### Fact Caching (중복 작업 제거)

`gathering = smart`를 설정하면 이미 수집된 시스템 정보(IP, OS 등)가 캐시에 있을 경우 다시 수집하지 않습니다. 수백 대의 서버 정보를 매번 새로 읽어오는 부하를 획기적으로 줄여줍니다.

## 3. AWS 환경에서의 성능 및 과금 포인트

### 제어 노드 인스턴스 사양 (유료 전환 및 비용)

* **CPU/Memory:** `forks` 수치를 높일수록 제어 노드의 메모리 사용량이 선형적으로 증가합니다. **t3.micro(1GB RAM)**에서 `forks=50` 이상을 사용하면 메모리 부족(OOM)으로 프로세스가 강제 종료될 수 있습니다.
* **권장:** 안정적인 수백 대 관리를 위해서는 **t3.medium(4GB RAM)** 이상의 인스턴스 사용을 권장합니다.

### SSH ControlPersist 비용

* `ControlPersist=60s` 설정은 연결이 끝난 후에도 60초간 SSH 세션을 유지합니다. 이는 다음 태스크 실행 속도를 높여주지만, 그만큼 제어 노드에서 프로세스가 떠 있게 됩니다.
* 이로 인해 발생하는 추가 과금은 없으나, **CPU 크레딧 소모**에 영향을 줄 수 있으므로 T 계열 인스턴스를 사용 중이라면 모니터링이 필요합니다.

### 네트워크 트래픽

* `pipelining`은 데이터 전송량을 줄여주므로, 리전 간(Inter-Region) 통신 시 발생하는 **Data Transfer Out 비용을 절감**하는 데 간접적인 도움을 줍니다.
