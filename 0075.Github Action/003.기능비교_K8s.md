## GitHub Actions vs Kubernetes (K8s) 종합 비교 분석

**GitHub Actions(GHA)**는 워크플로우 자동화 도구이며, **Kubernetes(K8s)**는 컨테이너 오케스트레이션 플랫폼입니다. 두 시스템은 목적이 다르지만, 최근에는 **ARC(Actions Runner Controller)**를 통해 K8s 내부에서 GHA 러너를 실행하거나, **GitOps**를 통해 GHA가 K8s의 상태를 제어하는 등 긴밀하게 상호작용합니다.

---

### 1. 종합 비교 및 설계 철학 분석

| 구분 | **GitHub Actions (CI/CD 자동화)** | **Kubernetes (컨테이너 오케스트레이션)** |
| --- | --- | --- |
| **주요 목적** | 소프트웨어 개발 수명 주기(SDLC) 자동화 | 컨테이너화된 애플리케이션 배포 및 운영 |
| **작동 원리** | **이벤트 기반 (Event-driven)** | **선언적 상태 유지 (Desired State)** |
| **설정 방식** | YAML (Workflow 명세서) | YAML (Manifest 명세서) |
| **유지보수** | SaaS형(GitHub 관리)으로 운영 부담 적음 | 매우 높은 운영 숙련도 필요 (직접 관리 시) |
| **실행 단위** | Step / Job (프로세스 실행) | Pod / Container (서비스 상주) |
| **확장성** | Marketplace의 Actions 활용 | Custom Resource Definition (CRD) 활용 |
| **장점** | 개발 흐름과 즉시 연동, 설정이 매우 빠름 | 자가 치유(Self-healing), 무중단 배포, 확장성 |
| **단점** | 장기 실행 서비스 운영에 부적합 | 초기 구축 비용 및 학습 곡선이 매우 높음 |

---

### 2. 기능 대칭 및 단독 기능 상세 비교

| 기능 카테고리 | **GitHub Actions** | **Kubernetes** | 비고 |
| --- | --- | --- | --- |
| **트리거 (Trigger)** | `on: push / schedule` | **Event / Watch (상태 감지)** | K8s는 상태가 변하면 반응 |
| **시간 예약** | `on: schedule` (Cron) | **CronJob** | - |
| **수동 조작** | `workflow_dispatch` | `kubectl apply / rollout` | - |
| **비밀값 관리** | `secrets` (GitHub 암호화) | **Secrets / ConfigMap** | K8s는 base64 인코딩 방식 |
| **실행 환경** | Hosted / Self-hosted Runner | **Node (Worker Node)** | - |
| **병렬 처리** | `strategy: matrix` | **ReplicaSet / Jobs** | - |
| **결과물 저장** | `upload-artifact` | **Persistent Volume (PV)** | K8s는 영구 저장 가능 |
| **환경 격리** | 가상 환경 (Virtual Environments) | **Namespace** | K8s는 논리적 그룹화 지원 |
| **에러 핸들링** | `continue-on-error` | **Liveness / Readiness Probe** | K8s는 컨테이너 재시작 지원 |

---

### 3. 도구별 단독/특화 기능 (Exclusive Features)

| **GitHub Actions 전용 기능** | **Kubernetes 전용 기능** |
| --- | --- |
| **네이티브 VCS 통합**: 코드 변경, 이슈, PR 등 개발 이벤트에 즉각 반응하는 최적의 CI 도구. | **자가 치유 (Self-healing)**: 컨테이너가 죽으면 설정된 복제본(Replicas) 수만큼 자동으로 다시 살림. |
| **Marketplace**: 수만 개의 사전 정의된 동작(Action)을 조합하여 복잡한 로직을 코드 없이 구현. | **서비스 디스커버리**: 내장된 DNS와 LoadBalancer를 통해 복잡한 마이크로서비스 간 통신 관리. |
| **Ephemeral Runner**: 매 작업마다 깨끗하게 지워지고 재생성되는 실행 환경 제공. | **오토스케일링 (HPA/VPA)**: 트래픽에 따라 컨테이너 개수를 자동으로 늘리거나 줄임. |

---

### 4. AWS 환경에서의 운영 및 과금 가이드 (통합 운영)

현업에서는 이 두 도구를 따로 보지 않고 **AWS EKS(Kubernetes)** 내부에서 **GitHub Actions Runner**를 운영하는 방식을 많이 사용합니다.

1. **Actions Runner Controller (ARC)**
* **구조**: AWS EKS 클러스터 안에 GHA 러너를 Pod 형태로 띄웁니다.
* **장점**: 빌드량이 많을 때만 Pod를 늘려 비용을 아끼고, 회사 내부망(VPC) 자원에 직접 접근할 수 있습니다.
* **과금 주의**: EKS 노드 자원을 사용하므로 **EC2 인스턴스 비용**이 발생하며, 빌드가 끝난 후 Pod가 제대로 삭제되지 않으면 자원 낭비가 생깁니다.


2. **보안 인증 (OIDC)**
* **GHA → K8s**: GitHub Actions에서 EKS로 배포할 때, IAM Role과 OIDC를 연동하면 Access Key 없이도 `kubectl` 명령어를 날릴 수 있어 보안상 매우 우수합니다.


3. **네트워크 및 데이터 전송**
* **과금 주의**: 외부(GitHub)에서 EKS로 대용량 이미지를 전송할 때 **Data Transfer Out** 비용이 발생할 수 있습니다. 동일 리전(Region) 내에서 러너를 운영하면 이 비용을 0원으로 만들 수 있습니다.
