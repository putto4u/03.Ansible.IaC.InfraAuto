## DB 마이그레이션 및 동적 복제 자동화 프로젝트

이 프로젝트는 인벤토리에 정의된 DB 서버 대수(2대, 5대 혹은 그 이상)를 Ansible이 스스로 판단하여, **쓰기 서버(Master)**에는 데이터를 주입(마이그레이션)하고 **읽기 서버(Slave)**들에는 복제 설정을 자동으로 전파하도록 설계되었습니다. 이전 웹 서버 및 로드 밸런서 프로젝트와 인벤토리 형식을 일치시켜 통합 운영이 가능합니다.

---

### 1. 동적 마이그레이션 및 복제 아키텍처

서버 대수에 상관없이 Ansible의 그룹 분기 로직을 통해 다음과 같이 작동합니다.

1. **동적 역할 인식**: `db_master` 그룹에 속한 첫 번째 서버를 마이그레이션 리더로 선정합니다.
2. **데이터 소스 동기화**: 마스터 서버가 인터넷에서 마이그레이션용 SQL 데이터를 다운로드합니다.
3. **순차적 복제 전파**:
* **Master**: 데이터를 주입하고 복제용 바이너리 로그 포지션을 생성합니다.
* **Slaves**: 인벤토리에 등록된 모든 슬레이브 서버가 마스터의 정보를 받아 실시간 동기화를 시작합니다.


4. **로드 밸런싱 준비**: 마이그레이션이 완료된 모든 서버는 읽기 로드 밸런서의 타겟으로 즉시 투입될 수 있는 상태가 됩니다.

---

### 2. 프로젝트 디렉토리 구조

이전 프로젝트의 `roles` 구조를 계승하여 확장성을 유지합니다.

```text
db-total-migration/
├── inventory.yml                # 관리할 DB 서버 리스트 (2대~N대)
├── deploy_migration.yml         # 전체 마이그레이션 실행 플레이북
└── roles/
    └── mysql_migration/
        └── tasks/
            └── main.yml         # 마스터 주입 및 슬레이브 복제 로직 (주석 포함)

```

### 3. 주요 파일별 소스 코드

#### ① 인벤토리 파일 (`inventory.yml`)

이전 프로젝트와 형식을 일치시켰으며, 서버가 늘어나면 `hosts` 아래에 추가만 하면 됩니다.

```yaml
all:
  children:
    db_master:                   # 마이그레이션 주체 (쓰기 서버)
      hosts:
        db_01: { ansible_host: 192.168.20.101 }
    db_slave:                    # 복제 대상들 (읽기 서버들)
      hosts:
        db_02: { ansible_host: 192.168.20.102 }
        db_03: { ansible_host: 192.168.20.103 } # 추가 서버도 자동 인식

```

#### ② 마이그레이션 및 복제 역할 (`roles/mysql_migration/tasks/main.yml`)

서버의 그룹을 판단하여 마스터와 슬레이브 작업을 자동으로 분기합니다.

```yaml
---
# [공통 작업] 마이그레이션 준비
- name: Git 설치 (데이터 다운로드용)
  ansible.builtin.apt:
    name: git
    state: present

# [Master 작업] 데이터 주입 및 마이그레이션
- name: 마스터 서버 데이터 마이그레이션 실행
  when: inventory_hostname in groups['db_master'] # 마스터 그룹일 때만 실행
  block:
    - name: 마이그레이션 데이터 다운로드
      ansible.builtin.git:
        repo: 'https://github.com/datacharmer/test_db.git'
        dest: /tmp/migration_data
        clone: yes

    - name: SQL 데이터 마스터 서버 주입
      ansible.builtin.shell:
        cmd: mysql -t < employees.sql
        chdir: /tmp/migration_data
      changed_when: true

    - name: 복제용 계정 생성 (Replication User)      # 슬레이브가 접속할 계정 생성
      mysql_user:
        name: repl_user
        password: "password123"
        priv: "*.*:REPLICATION SLAVE"
        host: "%"
        state: present

# [Slave 작업] 복제 자동 연결
- name: 슬레이브 서버 복제 설정 및 시작
  when: inventory_hostname in groups['db_slave']  # 슬레이브 그룹일 때만 실행
  block:
    - name: 마스터 서버와 동기화 설정                # 마스터의 IP를 보고 자동으로 연결
      mysql_replication:
        mode: changemaster
        master_host: "{{ hostvars[groups['db_master'][0]]['ansible_host'] }}"
        master_user: repl_user
        master_password: "password123"

    - name: 슬레이브 복제 프로세스 시작
      mysql_replication:
        mode: startslave

# [검증 작업]
- name: 마이그레이션 데이터 확인
  ansible.builtin.shell:
    cmd: mysql -e "SELECT count(*) FROM employees.employees;"
  register: db_status

- name: 각 서버별 데이터 보유 현황 출력
  ansible.builtin.debug:
    msg: "{{ inventory_hostname }}의 데이터 수: {{ db_status.stdout }}"

```

### 4. AWS 운영 및 과금 가이드

* **서버 대수에 따른 과금**: 인벤토리에 등록된 서버가 많을수록 **EC2 인스턴스 비용**과 **EBS 스토리지 비용**이 정비례하여 증가합니다.
* **유료 전환 주의 (EBS)**: 모든 DB 서버의 디스크 합계가 **30GB**를 넘지 않도록 설정하세요. (예: 서버 5대 가동 시 각 서버당 6GB 이하 권장)
* **네트워크 데이터 요금**: 마스터에서 여러 대의 슬레이브로 마이그레이션 데이터를 복제할 때, **가용 영역(AZ) 간 데이터 전송료**가 발생할 수 있습니다. 동일한 AZ에 서버를 배치하면 비용을 절감할 수 있습니다.
* **CPU 크레딧 소모**: 마이그레이션은 대량의 연산을 필요로 하므로 `t2.micro` 같은 프리티어 사양에서는 CPU 크레딧이 급격히 소모되어 서버가 느려질 수 있습니다.
* **실습 종료 후 조치**: 과금을 막기 위해 모든 인스턴스를 반드시 **Terminate(종료)** 하십시오.
