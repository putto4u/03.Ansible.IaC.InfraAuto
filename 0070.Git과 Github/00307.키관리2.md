## SSH 키 식별 및 관리 전략

`authorized_keys` 파일은 단순히 공개키 값만 나열되어 있어, 관리자가 많아질수록 어떤 키가 누구의 것인지 구분하기 매우 어렵습니다. 이를 해결하기 위해 **주석(Comment)** 기능과 **키 관리 규칙**을 활용해야 합니다.

---

### 1. 키 하단에 주석(Comment) 활용하기

SSH 공개키(`id_rsa.pub`)의 구조를 보면 마지막 부분에 생성 당시의 사용자 이름과 호스트명이 자동으로 붙습니다. 이를 활용하거나, 서버에 등록할 때 명시적으로 이름을 적어주면 됩니다.

* **형식:** `ssh-rsa [키_데이터] [이름/이메일/날짜]`
* **예시:**
```text
ssh-rsa AAAAB3Nza...[생략]... user_hong_gildong (2026-01-19)
ssh-rsa AAAAB3Nza...[생략]... user_lee_soonshin (laptop)

```


* `authorized_keys` 파일 내에서 키 데이터 바로 뒤에 한 칸 띄우고 적는 내용은 모두 주석으로 처리되어 인증에 영향을 주지 않습니다.



---

### 2. 별도의 매핑 테이블(문서) 운영

서버 내에서 텍스트로만 관리하는 것이 불안하다면, 엑셀이나 Markdown 문서를 통해 키의 지문(Fingerprint)과 실사용자를 매칭해두어야 합니다.

#### 키 지문(Fingerprint) 확인 방법

사용자에게 키 파일을 직접 받는 대신, 아래 명령어로 추출한 '지문'을 대조하여 누구인지 확인할 수 있습니다.

```bash
# 특정 키 파일의 지문 확인
ssh-keygen -l -f ./collaborator_key.pub

# 결과 예시: 4096 SHA256:abcd...123 user_hong (RSA)

```

---

### 3. SSH Key 옵션을 이용한 식별과 제한

단순히 이름만 적는 것을 넘어, `authorized_keys` 파일 내에서 특정 키마다 다른 권한을 부여할 수 있습니다. 이를 통해 누가 접속했는지 로그로 남기거나 기능을 제한할 수 있습니다.

```text
# 특정 IP에서만 접속 가능하도록 제한하고 주석 달기
from="192.168.1.10",no-agent-forwarding,no-pty ssh-rsa AAA... user_admin

# 특정 키로 접속 시 실행될 환경 설정
environment="GIT_USER=hong" ssh-rsa AAA... user_hong

```

---

### 4. 전문 관리 도구(Gitea, GitLab) 도입 권장

수작업으로 `authorized_keys`를 관리하는 것은 사용자 5명 이하일 때만 추천합니다. 그 이상이 되면 다음과 같은 이유로 **Gitea** 같은 GUI 도구를 쓰는 것이 훨씬 경제적입니다.

* **사용자 직접 등록:** 사용자가 웹 UI에서 직접 자신의 키를 등록/삭제합니다.
* **이름 매칭:** 시스템이 자동으로 어떤 키가 어떤 사용자의 것인지 데이터베이스로 관리합니다.
* **이력 관리:** 누가 언제 코드를 올렸는지 웹에서 바로 확인할 수 있습니다.

---

### 5. 인프라 운영 및 비용 고려 (AWS)

AWS 환경에서 여러 명의 키를 관리할 때 주의할 점입니다.

| 구분 | 관리 방법 | 과금 및 주의사항 |
| --- | --- | --- |
| **IAM Key** | AWS 서비스 접근용 | 사용자당 최대 2개의 키 생성 가능 (무료) |
| **EC2 SSH** | 서버 OS 직접 접속용 | `authorized_keys` 용량은 무시해도 될 수준이나, **관리 리소스(인건비)**가 발생 |

> **팁:** 사용자가 많아지면 서버를 직접 관리하는 시간 비용이 AWS의 관리형 서비스(CodeCommit 등) 비용보다 커질 수 있습니다. 하지만 공부나 소규모 프로젝트라면 주석 관리만으로 충분합니다.
